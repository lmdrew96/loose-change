# Codebase Review: Loose Change
**Date:** 2026-09-09
**Stack:** Next.js 16 (PWA) + Convex + Clerk + AssemblyAI, TypeScript
**Project type:** App with a hand-rolled MCP server (`lc_` tools)
**Previous review:** REVIEW-2026-07-22.md — all 10 findings shipped

## Executive Summary

Every finding from the July review landed, and the additions since (Kept archive,
swipe + keyboard triage, weekly resurfacing push, incremental recording persistence,
auth tests) are well-built. Typecheck and the production build are clean; 10 tests pass.

The gaps that remain cluster in one place: **the app is much better at capture than at
retrieval.** Once an entry leaves the untriaged state, its full text is clamped to two
lines with no way to expand, its audio becomes unplayable, and — separately — the audio
blob may already have been deleted by a retention job that measures from the wrong
timestamp. The other significant gap is that the PWA cannot cold-start offline, which
breaks the app's core promise in exactly the situation it was built for.

Nothing here needs an architecture change. The most expensive item is half a day.

## High Priority Findings

### 1. The PWA can't cold-start offline — and the offline page says it can

- **What**: `public/sw.js` precaches only `/offline` and `/manifest.webmanifest`. Navigations
  are network-first with the offline page as fallback. So opening the installed app with no
  signal shows `/offline` — a static screen with **no record button**. Meanwhile
  `src/app/offline/page.tsx:5-7` reads: *"Voice and text capture still work — entries save
  locally and sync once you're back online."* That is true of the sync layer and false of
  what the user is looking at.
- **Why it matters**: This is the driving-with-no-signal case the whole app exists for. The
  IndexedDB queue, incremental chunk persistence, and orphan salvage are all correct — they're
  just unreachable, because the shell that hosts them was never cached. The build output
  confirms `/` is prerendered static (`○`), so caching it is cheap and correct.
- **Suggested action**: Add `/` to `PRECACHE_URLS` and serve it cache-first (or
  stale-while-revalidate) for navigations to `/`. Keep `/offline` as the fallback for the
  other routes, which genuinely do need the network. Then fix the offline page copy to say
  which screens work.
- **Effort estimate**: Half-day

### 2. No entry detail view — the archive is effectively write-only

- **What**: Kept, Inbox, and Search all render transcripts with `line-clamp-2` and no expand
  affordance. There is no `/entry/[id]` route. Audio is only ever rendered in `TriageScreen`,
  which by definition shows untriaged entries. So the moment you Keep a voice memo, you can
  no longer read past its first two lines or listen to it — ever, from the UI.
- **Why it matters**: Two problems in one. First, retrieval is half the product. Second, it
  contradicts a stated README decision: *"No retry-transcription UI in v1. If a transcript
  comes back garbled, the audio stays playable alongside it — that's the fallback, not a
  re-run button."* The fallback isn't reachable where you'd need it. Note that
  `listByStatusHandler` (`convex/entries.ts:51-56`) **already generates and ships `audioUrl`
  for every Inbox and Kept row** — both screens type it in their `EntryCard` props and then
  never render it. The data is already paid for.
- **Suggested action**: Simplest version that closes it: make cards expandable in place
  (tap to unclamp) and drop the existing `AudioPlayer` into the expanded state for voice
  entries. A dedicated detail route is the fuller answer but isn't required. Extract
  `AudioPlayer` out of `TriageScreen.tsx` into its own file when you do.
- **Effort estimate**: Half-day

### 3. Audio retention measures from `createdAt`, not from when the entry was triaged

- **What**: `convex/retention.ts:9-14` computes `cutoff = now - 30d` and deletes audio for any
  kept/discarded/promoted entry with `createdAt < cutoff`. The README specifies: *"once an
  entry's status is kept, discarded, or promoted **and** 30 days have elapsed."* There is no
  `triagedAt` field, and `discardedAt` — which is written on every discard
  (`convex/entries.ts:89`) — is **never read by anything** (grep confirms: schema, three
  writes, zero reads).
- **Why it matters**: Two concrete failures. A memo captured 90 days ago and triaged this
  morning loses its audio at the next 08:00 UTC cron — hours after triage, not 30 days.
  And a memo discarded today whose `createdAt` is older than 30 days loses its audio
  immediately, so `undoDiscard` inside the advertised undo window restores a transcript-only
  husk. Combined with Finding #2, that's the one recovery path for a bad transcript gone.
- **Suggested action**: Add `triagedAt: v.optional(v.number())`, set it in `keepHandler`,
  `discardHandler`, and `markPromotedHandler`, and filter retention on it. Backfill existing
  rows to `createdAt` so behavior doesn't change for them. While in there, skip rows where
  `audioStorageId === null` in the query rather than in the loop (see Finding #7).
- **Effort estimate**: Half-day

### 4. Triage has no "skip" — the one screen that forces a decision per entry

- **What**: `TriageScreen` renders `results[0]` from a paginated query and advances only when
  a mutation removes the current entry from the untriaged set. Keep, Discard, Kindling, CC —
  every action commits. There is no way to say "not now" and see the next one; the only
  non-decision is to leave the screen entirely and restart from the same entry.
- **Why it matters**: The README's founding line is *"Capture must never require a decision."*
  Triage is allowed to require decisions — but one undecidable entry currently blocks the
  whole queue behind it, which is precisely the executive-function trap (decision paralysis →
  abandon the flow → inbox never gets triaged) the app is designed around. Everything else on
  this screen already respects that framing: untimed, no countdown, no cadence pressure.
- **Suggested action**: A fifth action or a small "Skip →" that advances a local index rather
  than mutating. Given `initialNumItems: 1`, this means holding an index into `results` and
  loading more as you pass the end, instead of always reading `results[0]`.
- **Effort estimate**: Half-day

## Medium Priority Findings

### 5. The service worker can cache the Clerk sign-in page as the offline fallback

- **What**: `ServiceWorkerRegistration` lives in the root layout, so it registers on
  `/sign-in` too. `/offline` is **not** in `proxy.ts`'s `isPublicRoute` matcher, so an
  unauthenticated `cache.addAll(["/offline", ...])` follows Clerk's redirect and caches a
  200 sign-in page under the `/offline` key. Anyone who installs before signing in gets a
  sign-in screen as their permanent offline experience.
- **Why it matters**: Silent, sticky, and only cleared by a `CACHE_NAME` bump.
- **Suggested action**: Add `/offline` to `isPublicRoute`. (Cheap belt-and-braces: register
  the SW only when authenticated.)
- **Effort estimate**: Quick fix

### 6. Discarded entries are never actually deleted — the 30-day window never closes

- **What**: No `ctx.db.delete` exists for `entries` anywhere (only `pushSubscriptions`).
  Retention nulls out `audioStorageId` and stops. So a discarded memo keeps its transcript
  forever and keeps surfacing in `lc_search` and the Search screen (which renders
  `· discarded` rows) indefinitely.
- **Why it matters**: The README frames discard as a 30-day undo window, which reads as
  "then it's gone." It isn't. That's a privacy expectation mismatch on personal voice
  transcripts, plus unbounded table growth.
- **Suggested action**: Decide explicitly, then make the code and README agree: either purge
  discarded entries past 30 days in the same cron, or reword discard as a permanent
  soft-archive. Purging is the smaller change and matches the stated promise.
- **Effort estimate**: Quick fix (plus a decision)

### 7. Four unbounded `.collect()` calls that grow with usage

- **What**: `getUntriagedCount` (`entries.ts:215-219`) collects every untriaged row to call
  `.length`; `getStatsHandler` collects **every entry the user has ever made**;
  `getRandomKeptEntry` (`pushData.ts:59-62`) collects every kept entry to pick one;
  `deleteExpiredAudio` collects across **all users** per status, including the rows whose
  audio is already `null` (which becomes the overwhelming majority over time).
- **Why it matters**: Convex caps a single function's reads. `getUntriagedCount` runs on the
  Record screen — the hottest path in the app — and `getStatsHandler` backs `lc_get_stats`.
  These are fine today and will fail eventually, quietly, in an app explicitly designed to
  accumulate. Retention is the one that fails first, since it spans all users.
- **Suggested action**: For retention, `.take(N)` per run (idempotent, catches up over days)
  and skip null-audio rows in the query. For counts, either accept a cap
  (`.take(500)` → "500+") or maintain a running counter. Not urgent — but worth a note in
  the code so it isn't a surprise.
- **Effort estimate**: Half-day

### 8. Long transcripts are unreachable in Triage on mobile

- **What**: The swipe card carries `touch-none` (`TriageScreen.tsx:154`) to make pointer
  dragging work, and neither the card nor its container has `overflow-y-auto`. The four
  action buttons sit after the card in normal flow.
- **Why it matters**: A long voice memo makes the card taller than the viewport. `touch-none`
  means dragging on the card — i.e. most of the screen — won't scroll the page, and the
  Keep/Discard buttons are pushed below the fold. The entry becomes both unreadable and
  un-triageable without hunting for the padding gutter to scroll on.
- **Suggested action**: Give the card a `max-h` with `overflow-y-auto` on an inner wrapper
  that stops pointer propagation (same trick `AudioPlayer` already uses at line 302), and/or
  pin the action grid with `sticky bottom-0`.
- **Effort estimate**: Quick fix

### 9. `lc_undo_discard` lies about what it did

- **What**: The tool description says *"Restore a discarded entry back to untriaged"*
  (`mcp.ts:98`) and the response hardcodes `{ status: "untriaged" }` (`mcp.ts:225`). Since
  the `discardedFromStatus` work, undo restores to **kept** for anything discarded from the
  Kept screen — which `convex/entries.test.ts:83-94` explicitly tests for.
- **Why it matters**: Claude reads that description to decide when to call the tool and reads
  the response to report back. Both are now wrong, so an MCP client will confidently tell you
  a memo went back to your inbox when it went back to your archive.
- **Suggested action**: Return the real status from `mcpUndoDiscard` and pass it through;
  update the description to "Restore a discarded entry to the status it was discarded from."
- **Effort estimate**: Quick fix

### 10. Sync has no idempotency key — flaky networks can duplicate captures

- **What**: `syncOne` uploads the blob, calls `createVoiceEntry`, and only then does
  `deletePendingCapture` run. If the mutation commits but the response is lost (mobile
  handoff, tab killed), the capture stays queued and re-syncs into a second entry. `localId`
  is generated and used locally but never sent to Convex.
- **Why it matters**: Duplicates in the inbox mean triaging the same thought twice — low
  stakes individually, corrosive to trust in a capture tool.
- **Suggested action**: Send `localId`, store it on the entry with an index, and no-op the
  insert if it already exists.
- **Effort estimate**: Half-day

### 11. Clipboard failures leave "Send to Kindling/CC" looking dead

- **What**: `handleSendTo` (`TriageScreen.tsx:106-111`) and `handleCopy`
  (`SettingsScreen.tsx:47-52`) both `await navigator.clipboard.writeText(...)` with no
  try/catch. `writeText` rejects on a non-secure context, denied permission, or an iOS Safari
  gesture-window miss.
- **Why it matters**: On rejection the handler throws before `markPromoted`, so the button
  does visibly nothing and no toast fires. The ordering is right (nothing gets marked
  promoted on a failed copy) — it's only the silence that's the bug. Note the README's
  "no silent failures" spirit and that this is the sole handoff mechanism to the other apps.
- **Suggested action**: try/catch → `flashToast("Couldn't copy — check clipboard permissions")`.
- **Effort estimate**: Quick fix

### 12. The weekly reminder can't take you to the idea it showed you

- **What**: `sw.js:38-41` opens `/search` on notification click. The Search screen opens with
  an empty box and shows results only after you submit a query. The push payload carries the
  transcript text but no entry id.
- **Why it matters**: The notification's whole job is resurfacing one specific kept idea. It
  hands you a blank search field instead. `/kept` — which now exists — would land you on the
  archive at minimum.
- **Suggested action**: Open `/kept`. Better: include the entry id in the payload and deep-link
  once Finding #2 gives entries an addressable view.
- **Effort estimate**: Quick fix

### 13. `pnpm lint` fails on main

- **What**: `react-hooks/set-state-in-effect` errors on `TriageScreen.tsx:50` — the effect
  that resets `dragX`/`flying` when the entry changes. Plus 5 warnings (4 stale
  `eslint-disable` directives in `convex/_generated`, 1 anonymous default export in
  `auth.config.ts`).
- **Why it matters**: A red lint gate that stays red stops being a gate. This is also a real
  cascading-render smell, not just a style rule.
- **Suggested action**: Extract the swipe card into its own component with `key={entry._id}` —
  React then discards the drag state on entry change and the effect disappears entirely.
- **Effort estimate**: Quick fix

## Low Priority / Nice-to-Have

### 14. Four unlabeled icons in the Inbox header

`InboxScreen.tsx:55-69` puts Search / Triage / Kept / Settings side by side as icon-only
links with `aria-label` only. This is a direct consequence of shipping July's Finding #7
(which asked for icon buttons over text links for visual consistency) — and on the ND lens
it's a regression, not an improvement: icon-only navigation is a named anti-pattern, and four
adjacent unlabeled glyphs is the worst case of it. Suggest tiny text labels under the icons,
which keeps the icon-first look and restores the affordance. **Quick fix**

### 15. No `prefers-reduced-motion` handling anywhere

Grep finds zero `motion-safe`/`motion-reduce`/media queries. The recording button runs
`animate-pulse` — an infinite animation — the entire time you're recording, against the
README's own *"No autoplay audio/animation"* constraint. The swipe card also animates
transform + rotate. Suggest `motion-safe:animate-pulse` and a reduced-motion guard on the card
transition; the recording state is already carried by color and the Stop icon, so nothing is
lost. **Quick fix**

### 16. Swipe intent is signaled by border color alone

Dragging right turns the border gold, left turns it red (`TriageScreen.tsx:154-160`), with no
text or icon. Color-as-sole-indicator, and gold/red on a dark green ground is a rough pairing
for red-green color blindness. A "Keep" / "Discard" word fading in with the drag fixes it and
also makes the gesture discoverable. **Quick fix**

### 17. No elapsed-time indicator while recording

Nothing on screen says how long you've been recording. Time perception under ADHD is exactly
what a timer scaffolds, and there's a real ceiling behind it: `MAX_POLL_ATTEMPTS × POLL_INTERVAL`
caps AssemblyAI polling at 150s, after which the entry silently lands as
`transcriptionStatus: "failed"`. A `mm:ss` counter is a few lines. **Quick fix**

### 18. Install banner never stays dismissed, and covers the Triage buttons

`InstallPrompt` keeps dismissal in component state only, so "Not now" lasts until the next
navigation. It's also `fixed bottom-0 z-50`, which sits on top of the Triage action grid and
the Kept screen's undo toast (`bottom-6`, also `z-50`). Persist the dismissal to `localStorage`
and render the banner only on `/`. **Quick fix**

### 19. Regenerating the MCP token has no confirmation

`SettingsScreen`'s Regenerate silently invalidates every configured MCP client with no confirm
and no warning copy — the app's one genuinely irreversible action. A line of copy plus a
confirm step. Separately, `role="status" aria-live="polite"` is on the Copy *button* itself
(line 149-152) rather than a sibling status element; it works by accident. **Quick fix**

### 20. Smaller items

- No `lc_list_kept` MCP tool — the archive is only reachable from MCP via a search term, though
  the UI now has a browse screen. Natural addition alongside `lc_list_inbox`.
- Promoted entries have no browse surface at all (not in Inbox, not in Kept, only via Search).
- `package.json` has no `clean` script, but the project's own pre-commit ritual is
  `pnpm clean && pnpm build`.
- Test coverage is auth + discard/undo only. The untested code that actually destroys data is
  `retention.ts`; `offlineQueue`'s chunk-serialization chain and `dispatchTool`'s arg coercion
  are the next most valuable.
- `.env.example` has uncommitted changes (the Clerk sign-in/up URL vars) and
  `REVIEW-2026-07-22.md` is untracked — worth committing so the env contract isn't only in
  someone's working tree.

## Dimension Summaries

### UI/UX: 🟡 Consistent and genuinely minimal; retrieval and motion are the weak spots
The visual language holds together and the July accessibility pass stuck (contrast token
lightened with the reasoning in a comment, `aria-live` on toasts). What's left is Findings
#2, #8, #14–#17 — reachability and sensory items, all fixable inside the existing language.

### Features: 🟡 Capture is complete; retrieval is half-built
Record → transcribe → Inbox → Triage → Kept → retention → MCP all work end to end. The gaps
are the ones a user hits *after* triage: can't read the whole thing, can't hear it, can't
skip an undecidable entry, and can't reliably act on what Search turns up.

### MCP: 🟢 Nine tools, clean two-layer trust boundary, one stale description
The `dispatchTool` switch covers every tool in `TOOLS` with no orphans, and the token →
shared-secret → `mcp*` layering is well-reasoned and well-commented. Finding #9 is the only
correctness issue; `lc_list_kept` is the only obvious missing tool.

### Architecture: 🟢 The shared-handler pattern is still the best thing in here
One implementation per operation serving both the Clerk path and the MCP path. Strict TS,
no `any`, clean build. Watch the `.collect()` calls (#7) and the `discardedAt` field that
nothing reads (#3/#6) — dead fields are how schemas start lying.

### Infrastructure: 🟡 Everything is right except the service worker
Manifest complete, icons complete, env contract documented, build clean. The SW is the one
piece that doesn't deliver what the rest of the offline stack was built for (#1, #5).

### DX: 🟡 Great docs, real tests, red lint
README-to-code fidelity is still unusually high and the code comments explain *why*
(the webm-duration hack, the pointer-capture stop, the IndexedDB serialization chain) rather
than restating *what* — keep doing that. Lint failing on main (#13) undercuts it.

## Strengths

- **The July review actually got implemented.** All ten findings, plus five features on top.
  That's a rare follow-through rate and the main reason this review could go deeper.
- **Comments explain the non-obvious.** `AudioPlayer`'s Infinity-duration workaround, the
  `onPointerDown` stop-propagation, `recordingOpsChain`'s two named race conditions, the
  `discardedFromStatus` migration note. Every one of these is a thing a future reader would
  otherwise break.
- **Incremental recording persistence.** Chunks hit IndexedDB every 5s and orphans are salvaged
  at boot, so a phone call mid-memo costs you 5 seconds, not the memo. That's real engineering
  against the actual use case.
- **The shared-handler architecture** — one code path per operation across two trust boundaries.
- **Design constraints are still honored**, not just documented: no infinite scroll, no streaks,
  plain counts, reversible discard, one primary action on Record. The weekly push is framed as
  resurfacing a kept idea rather than nagging about the backlog — that's the constraint being
  understood, not just followed.
