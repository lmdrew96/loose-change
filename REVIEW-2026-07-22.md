# Codebase Review: Loose Change
**Date:** 2026-07-22
**Stack:** Next.js (PWA) + Convex + Clerk + AssemblyAI, TypeScript
**Project type:** App with an MCP server (`lc_` tools)

## Executive Summary
Loose Change is in excellent shape for its stage — the README spec and the shipped code line up almost line-for-line, the record→transcribe→triage loop is fully wired end to end, and the minimal visual language (solid fills, no shadows/gradients, one primary action per screen) is genuinely honored rather than just stated. The biggest gaps aren't about adding UI chrome — they're about a couple of promises the README makes (30-day reversible discard, offline-safe capture) that the backend supports but the UI doesn't yet surface a way to reach. All of the fixes below are things you can do *within* the current minimal visual language — small text/icon additions to screens that already exist, not new screens or nav.

## High Priority Findings

### 1. The 30-day undo window is real in the data model but unreachable from the UI after ~6 seconds
- **What**: `discardEntry`/`undoDiscard` fully support restoring a discarded entry any time in its 30-day retention window (`convex/entries.ts`), and the README lists "every destructive action (Discard) is reversible for 30 days" as a hard design constraint. But in the UI, `TriageScreen.tsx` only shows the Undo toast for 6 seconds after a Discard (`setTimeout(..., 6000)`), and there's no other screen where a discarded entry can be found and undone. `SearchScreen.tsx` will surface discarded entries in results (it shows `· {entry.status}`) but has zero action buttons — you can see a discarded entry exists, but not undo it.
- **Why it matters**: For anyone using the app through the web UI (not an MCP client), "reversible for 30 days" is only true for 6 seconds. That's a real gap between the stated design constraint and what a human user can actually do.
- **Suggested action**: Give Search result rows an "Undo" action when `status === "discarded"` — the mutation (`undoDiscard`) already exists, this is just a button. No new screen needed.
- **Effort estimate**: Half-day

### 2. Sync failures are silent — no user-facing signal that a capture never made it to Convex
- **What**: `syncEngine.ts` catches per-capture sync errors and only `console.error`s them, leaving the item in the IndexedDB queue to retry on the next `online` event or app load. There's no UI anywhere that shows "N captures pending sync" or flags a capture that's failed repeatedly.
- **Why it matters**: The Record screen shows "Saved ✓" the instant a capture is queued locally, which is the right call for the "never blocks on network" design goal — but if sync then fails permanently (expired upload URL, transient 500 that never gets a retry trigger, etc.), the user has no way to know their memo never left the device. That's a silent data-loss risk for exactly the driving/half-asleep captures this app is built to protect.
- **Suggested action**: A small, low-key pending-count indicator (e.g. next to the inbox icon on Record screen, sourced from `getPendingCaptures().length`) — consistent with the "plain number, no red badges" philosophy already used for the untriaged count.
- **Effort estimate**: Half-day

### 3. MCP bearer token is generated with `Math.random()`, not a CSPRNG
- **What**: `mcpTokens.ts`'s `generateToken()` builds a 40-char token from `Math.random().toString(36)` — its own comment acknowledges this isn't a real CSPRNG, reasoning that "Convex mutations can't use Node's crypto." That's true for Node's `crypto` module, but this token is the *sole* credential gating full read/write access to a user's personal (voice) transcripts via a public URL (`/{token}/mcp`) — it's worth confirming whether `globalThis.crypto.getRandomValues` (Web Crypto, not Node crypto) is available in Convex's mutation runtime before settling for `Math.random()`. If it isn't available in mutations, generate the token in a Convex **action** (which does have broader runtime access) and pass it to a mutation for storage.
- **Why it matters**: `Math.random()`'s output (V8's xorshift128+) is not cryptographically unpredictable. For a long-lived bearer token protecting personal data, that's a meaningfully weaker guarantee than it needs to be, for close to zero extra cost.
- **Suggested action**: Verify Web Crypto availability in the Convex runtime layer you're generating in; swap to `crypto.getRandomValues` (or generate in an action) accordingly.
- **Effort estimate**: Quick fix (~1hr, once verified)

## Medium Priority Findings

### 4. Search results are read-only — no way to act on what you find
- **What**: `SearchScreen.tsx` renders matched entries with no buttons at all. If you search and find something you want to keep, discard, or promote, there's no way to do it from that screen — you'd have to remember it and hope it resurfaces in Triage (which only shows untriaged entries, so a *kept* or *discarded* entry found via search can never be acted on from the UI at all).
- **Why it matters**: Search is currently the only way to browse anything beyond the untriaged inbox — making it purely read-only turns every search into a dead end for anything but untriaged items.
- **Suggested action**: At minimum, wire the Undo action described in Finding #1 into search rows. Full keep/discard-from-search is a nice-to-have beyond that.
- **Effort estimate**: Half-day

### 5. Secondary text color fails WCAG AA contrast on the dark background
- **What**: `text-beaver` (`#948870`) on `bg-jungle` (`#15342e`) computes to **~3.85:1** contrast — below the 4.5:1 WCAG AA minimum for normal-size text. It's used throughout for timestamps, capture-mode icons, helper copy, and nav links (`InboxScreen`, `TriageScreen`, `SearchScreen`, `SettingsScreen`). The `text-beaver/60` variant used for placeholder text (`RecordScreen`'s textarea) is even lower-contrast.
- **Why it matters**: This text carries real information (timestamps, entry counts, status), not just decoration — low-vision users may not be able to read it comfortably against the dark theme.
- **Suggested action**: Lighten the beaver token slightly, or reserve full-opacity beaver for anything below ~14px and avoid the `/60` opacity variant on body text.
- **Effort estimate**: Quick fix

### 6. Toasts have no `aria-live` region
- **What**: The Undo toast and "Copied — paste into…" toast in `TriageScreen.tsx` (and the Copy confirmation in `SettingsScreen.tsx`) are plain divs with no `role="status"`/`aria-live`. Confirmed by grep — there's no `aria-live` usage anywhere in `src/`.
- **Why it matters**: Screen reader users get no announcement that a Discard happened or that the 6-second Undo window is open — for the one destructive action in this app, that's the moment feedback matters most.
- **Suggested action**: Add `role="status" aria-live="polite"` to the toast containers.
- **Effort estimate**: Quick fix

## Low Priority / Nice-to-Have

### 7. Inbox header nav breaks from the icon-first pattern used everywhere else
- **What**: Every other screen uses a single icon back-button in the header. `InboxScreen.tsx`'s header instead has three underlined text links (Search / Triage / Settings) side by side.
- **Why it matters**: Minor visual inconsistency in an otherwise very consistent, minimal UI language — worth tightening since minimalism is the explicit goal here.
- **Suggested action**: Swap the three text links for icon buttons matching the rest of the app's header pattern.
- **Effort estimate**: Quick fix

### 8. No way to browse "kept" entries without knowing a search term
- **What**: The only way to see kept/archived entries is via `SearchScreen`, which requires typing a query — there's no plain reverse-chronological list of everything you've kept, unlike Inbox's paginated list of untriaged items.
- **Why it matters**: Minor — but if you just want to skim recent keeps without a search term in mind, there's currently no way to.
- **Suggested action**: Optional. If added, mirror Inbox's existing paginated (non-infinite-scroll) pattern rather than introducing a new one.
- **Effort estimate**: Half-day

### 9. Header icon tap targets are ~36px against the app's own "usable while driving, one-handed" bar
- **What**: Icon-only header buttons (inbox link, keyboard toggle on Record screen, back arrows) use `p-2` around a ~20px icon (~36px total tap area). The README calls out one-handed/driving usability specifically for the Record screen's primary controls (which are appropriately large at 128px).
- **Why it matters**: Minor for these secondary actions, but worth a note given the app's own stated context of use.
- **Suggested action**: Consider bumping to `p-3` (44px) on Record screen's header icons specifically, since it's the screen used mid-task.
- **Effort estimate**: Quick fix

### 10. No tests around the ownership/auth checks
- **What**: `requireOwnedEntry` and `requireMcpSecret` are the only things standing between one user's entries and another's — there are no test files anywhere in the repo.
- **Why it matters**: This is exactly the kind of logic that's cheap to regression-test and expensive to get wrong silently (cross-user data leak). Not urgent for a single-user-so-far MVP, but worth having before this gets more users.
- **Suggested action**: A couple of focused Convex function tests for `requireOwnedEntry` (wrong-user access throws) and `requireMcpSecret` (wrong/missing secret throws).
- **Effort estimate**: Half-day

## Dimension Summaries

### UI/UX: 🟡 Solid minimal foundation, with a real contrast issue and two reachability gaps
Visual language is consistent and genuinely minimal (see Strengths). Findings #1, #4, #5, #6, #7, #9 above are the actionable items — none of them require adding screens or chrome, just tightening what exists.

### Features: 🟡 Core loop fully wired; the undo/archive reachability gap is the standout issue
Record → transcribe → Inbox → Triage → retention is completely implemented and matches the README's build order. The MCP tools (`lc_capture_text`, `lc_mark_promoted`, etc.) are all wired too. Finding #1 is the one gap that undercuts a stated design guarantee.

### MCP: 🟢 All 9 documented tools implemented, consistent, well-documented trust boundary
`dispatchTool` covers every tool in the `TOOLS` array with no orphans. The two-layer auth model (per-user token → shared secret → Convex `mcp*` functions) is explained clearly in code comments and is architecturally sound. Only note is Finding #3 (token entropy).

### Architecture: 🟢 Clean shared-handler pattern
Client-facing mutations (Clerk-authed) and MCP-facing mutations (secret-authed) both call the same handler functions (`keepHandler`, `discardHandler`, etc.) in `convex/entries.ts` — avoids logic duplication across the two trust boundaries. TypeScript strict mode is on and honored; no stray `any`.

### Infrastructure: 🟢 Correctly minimal for the stage
Service worker is a small, purpose-built network-first-with-offline-fallback (no over-engineered caching strategy). `.env*` properly gitignored, no build artifacts tracked. PWA manifest is complete.

### DX: 🟡 Excellent README, no test coverage
The README is unusually accurate to the shipped code — data model, MCP tool table, and screen behavior all match implementation. That's rare and worth preserving as the project grows. Missing piece is Finding #10.

## Strengths
- **README-to-code fidelity**: the spec document and the implementation agree almost exactly — a strong signal of disciplined building, not scope creep.
- **Design constraints are actually honored**: no streaks, no infinite scroll, no forced categorization, plain untriaged counts — these aren't just README bullet points, they show up correctly in the components.
- **Shared-handler architecture**: one implementation of each mutation/query serving both the authenticated web client and the MCP shared-secret path — a clean way to avoid two divergent codepaths for the same operation.
- **Offline-first capture done right**: IndexedDB queue + background sync correctly decouples "Saved ✓" from network state, matching the core promise that capture never blocks.
